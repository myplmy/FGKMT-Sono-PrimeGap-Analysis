# 사용자 실행·전체 로그·완료 실행기 보존 규약

이 문서는 사용자가 직접 실험을 실행하고 Codex가 로그를 검토하는 연구에서 반복된 문제를 줄이기 위한 상세 절차다. 항상 적용할 짧은 불변식은 루트 `AGENTS.md`가 정본이다.

## 1. 상태를 네 가지로 분리한다

다음 표현을 섞지 않는다.

1. `IMPLEMENTED`: 코드와 실행기가 있음
2. `LOCALLY_VERIFIED`: parser, toy test, approval-denial 같은 비실험 검증을 통과함
3. `USER_RUN_FAILED`: 사용자가 실제 명령을 실행했지만 terminal PASS 또는 필수 산출물이 없음
4. `EXPERIMENT_PASS`: 승인 실행의 exit 0, terminal PASS, manifest, 결과 재검증이 모두 확인됨

코드가 준비됐거나 unit test가 통과했다는 이유만으로 실제 실험을 완료했다고 쓰지 않는다. 사용자가 붙여 준 콘솔 일부보다 원본 로그와 산출물을 먼저 확인한다.

## 2. 사용자에게 명령을 요청하는 형식

권장 작업과 핸드오프의 각 항목에는 다음을 반드시 함께 쓴다.

- 작업 목적
- 실행 환경: Windows CMD/Conda Prompt, PowerShell, 또는 WSL Ubuntu
- 시작 디렉터리
- 복사해 실행할 정확한 명령
- 예상 시간과 자원 한도
- 생성될 로그·산출물 경로
- 정상 종료 marker와 실패 시 멈출 지점
- 사용자가 Codex에 돌려줄 정보

사용자가 실행할 명령이 없으면 정확히 `별도 수행절차 필요없음`이라고 쓴다.

## 3. 한 실행기에는 한 승인 범위만 둔다

- P005는 WSL Ubuntu의 `.sh`를 사용한다. Windows BAT가 WSL을 대신 호출하지 않는다.
- Windows 연구 실행기는 고정 FGKMT Python을 쓰고, WSL이 필요한 작업은 `.sh`로 직접 제공한다. Windows BAT가 WSL을 대신 호출하지 않는다.
- 승인 flag가 없거나 추가 인자가 있으면 계산 전에 거부한다.
- 실제 데이터 범위, CPU/GPU, 메모리, 결과 경로가 다른 실험을 한 승인으로 묶지 않는다.
- GPU 금지 실험은 build target, 실행 로그, manifest에 `gpu_used=false`를 남긴다.

## 4. 로그는 성공 출력과 실패 출력을 모두 보존한다

새 장시간 Windows runner의 권장 경로는
`scripts/common/live_native_tee.py`와 `Invoke-LiveLoggedNativeStage`다. PowerShell의 .NET
`Start-Process` capture를 쓰지 않고 고정 FGKMT Python이 child stdout·stderr를 동시에 drain한다.
각 줄은 현재 PowerShell 화면에 즉시 표시되고 같은 main run log에도 append·flush된다. log에는
stream 전환 marker와 정확한 child exit code가 남는다.

기존 `Invoke-LoggedNativeStage`는 호환성을 위해 stdout과 stderr를 별도 임시 파일로 받은 뒤
종료 후 main log에 복사한다. 완료 runner의 bytes는 바꾸지 않으며, 아직 실행 전인 새 revision부터
live broker를 사용한다. 두 경로 모두 다음을 보존한다.

- 정상 stdout
- unittest 진행처럼 정상적인 stderr
- 빈 줄
- Python traceback
- stage 이름과 exit code
- PowerShell exception type, message, category, invocation line, stack, 전체 ErrorRecord
- 결과·로그 경로

Windows PowerShell 5.1에서 `& python ... 2>&1 | Tee-Object`와 `ErrorActionPreference=Stop`을 함께 쓰지 않는다. 정상 stderr를 `NativeCommandError`로 오인할 수 있다. 빈 문자열을 mandatory string parameter에 넘겨 로그 수집 자체가 실패하지 않도록 empty line을 명시적으로 허용한다.

live broker의 console 출력은 stdout 한 채널로 안전하게 mirror하지만 main log에는 원래 stdout과
stderr의 stream 전환을 표시한다. 이는 PowerShell 5.1의 `NativeCommandError` 오인을 피하기 위한
표시 계층의 선택이며, child stderr 내용이나 traceback을 삭제하거나 성공으로 바꾸지 않는다.

Windows PowerShell 5.1에서 Python broker에 argument array를 전달할 때 raw JSON argv를 직접
넘기지 않는다. UTF-8 JSON을 Base64 한 문자열로 운반하고 Python에서 Base64→UTF-8→JSON array
순서로 검증·복원한다. quote·space·backslash·한글 round-trip과 invalid Base64/JSON failure
logging을 regression test로 유지한다.

WSL helper는 시작부터 `exec > >(tee log) 2>&1`로 전체 shell 출력을 보존한다. run root를 만든 뒤 ERR/EXIT trap을 설치하고, 실패 시 `manifest.failed.txt`에 stage, exit code, 명령, line, 설정, 생성된 DB·metrics·부분 unknown hash를 남긴다. SQLite를 쓰는 upstream 도구는 계산 전에 `schema.sql`로 장부를 만들고 필수 table을 검사한다.

## 5. 실패 분석 순서

1. 원본 log 경로, byte size, SHA-256을 기록한다.
2. 마지막 PASS, 첫 FAIL, terminal marker 존재 여부를 찾는다.
3. result directory와 manifest 존재를 확인한다.
4. 계산 실패인지 runner/환경 실패인지 분리한다.
5. 실패 뒤 생성된 파일은 partial로 표시하고 성공 결과에 사용하지 않는다.
6. 같은 원인이 재현되면 새 결과로 해석하지 않고 동일 원인의 반복으로 기록한다.
7. 수정 후에는 실제 실험 대신 parser, toy logging self-test, approval-denial, 전체 unit test부터 통과시킨다.
8. 새 실제 실행에는 새 run ID와 별도 사용자 승인이 필요하다.

## 6. 실행된 BAT/PS1/SH와 전용 helper 보존

사용자가 실제 실행했다고 확인한 BAT/PS1/SH는 당시 bytes와 SHA-256을 확인한 뒤
`test_done/<name>-done.<ext>`로 이관한다. 완료 실험에만 쓰이고 다시 사용할 필요가
없는 helper와 fixture 검사도 같은 run과 연결해 이관한다.

- `test_done` 파일은 수정·재실행하지 않는다.
- 재실행이 필요하면 `scripts/experiments/<experiment>/`에 새 revision runner를 만든다.
- 같은 이름의 done 파일이 이미 있으면 덮어쓰지 않고 UTC/revision을 붙인다.
- 큐나 자동 탐색은 모든 `*-done.*`를 실행 대상으로 선택하지 않는다.
- done은 “실행됨”을 뜻할 뿐 “성공함”을 뜻하지 않는다. 성공 판정은 로그와 manifest가 담당한다.

여러 실험에서 다시 쓰는 기능은 완료 runner 안에 복사해 두지 않는다.

- 공통 로그·stage 처리: `scripts/common/`
- 일반 pipeline runner: `scripts/runners/`
- 공통 parser·failure semantics test: `scripts/tests/`
- 설치 helper: `scripts/setup/`

완료 원본은 내용까지 고쳐 재사용하지 않고, 재사용 기능을 새 모듈로 추출한 뒤 hash가
보존된 원본을 `test_done`에 둔다.

이관의 상세 판단은 `.agents/skills/runner-retirement/SKILL.md`를 따른다. 실행되지 않은 runner,
공통 source, 다음 단계가 읽는 `READY`·checkpoint·raw evidence는 이관하지 않는다.

## 7. 사용자와의 설명 방식

결과를 다음 순서로 쉬운 말부터 설명한다.

1. 무엇을 알아보려 했는가
2. 실제로 어디까지 실행됐는가
3. 성공한 부분과 실패한 부분
4. 실패가 연구 가설·수학 코드·실행기 중 무엇을 의미하는가
5. 지금 결과로 말할 수 없는 것
6. 다음에 사용자가 할 정확한 절차

전문 용어가 필요하면 바로 뒤에 일상어 뜻을 붙인다. 상한, certificate, coverage처럼 서로 다른 개념은 예시로 구분한다.

## 8. 시각화 확인

코드 수준에서는 축 범위, finite 값, 행 수, 파일 hash를 자동검사한다. 실제 그래프의 글자 겹침, 범례, 색, 잘림, 읽기 쉬움은 생성 후 사용자에게 시각검사를 요청한다. 사용자의 확인 전에는 `visual QA PASS`라고 쓰지 않는다.

## 9. READY·자원·결과 lifecycle

- WSL이 만든 `READY.txt`와 raw primecount evidence는 downstream Windows 실험과 결과감사가 끝날
  때까지 `tmp`에 있어도 `RETAIN`한다.
- process-tree memory ceiling 적용 여부와 observed peak RAM은 다른 값이다. peak를 측정하지
  않았으면 `not measured`라고 쓴다.
- runtime은 expected full path, possible early exit, hard wall, observed elapsed를 분리한다.
- actual result의 내부 label이 틀렸더라도 artifact를 소급 수정하지 않는다.
- 장기실행 상태는 PID·child tree·heartbeat·file write time·terminal marker를 함께 감사한다.
